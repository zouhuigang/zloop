# `zloop status` 逐元素审查（2026-08-28）

方法：脚本造出全部 8 种状态，各抓一屏真实输出（`COLUMNS=88`），逐个元素问三个问题——
**看得懂吗？是黑话吗？缺东西吗？** 判定只有三种：✅ 看得懂 / ⚠️ 要改 / ❌ 缺失。

用户的两个诉求作为验收尺子：
1. **一眼看出任务处于什么阶段**；
2. **一眼看出还剩哪些待办、每条该敲什么指令**。

## 一、标题行

| 元素 | 现状 | 判定 |
|---|---|---|
| 图标 + 状态词 | `✅ 完成` / `🔄 执行中` / `💤 休眠中` / `▶ 就绪` / `⏳ 等你决定` / `⏱ 限流中` / `⛔ 已停` / `⏸ 已暂停` | ✅ 八种词都是人话 |
| 进度条 + 百分比 | `████░░░░ 25%` | ✅ |
| `0/4 todo` | 完成数 / 总数 | ⚠️ 中英夹一半；`完成 0/4` 更直白 |
| `3 轮` | 执行过的轮次 | ⚠️ "轮"是内部黑话，用户不一定知道一轮 = 一次执行 |
| `$2.31/5.00` | 已花 / 上限 | ⚠️ 斜杠后面是什么看不出来，要写成 `上限 $5.00` |
| **它是"阶段"这件事** | 状态词本身就是阶段，但没有任何标签这么说 | ❌ **主诉求 1 没被满足**：用户看到的是一个词，不是"当前阶段" |

## 二、待办区

| 元素 | 现状 | 判定 |
|---|---|---|
| `▶ t1 [P0] 文本` | 下一条会被执行的 | ⚠️ 符号能猜，但没写"下一个" |
| `○ t2 …` | 排队中 | ⚠️ 猜不出是"排队"还是"没人管" |
| `! t3 …` + `↳ 问题` | 被 `--block`，问题印在下一行 | ⚠️ 问题看得懂，但 `!` 本身没说明是在等**你**回话 |
| `⏳ t4 …` | 等前置 todo | ⚠️ 和 `!` 视觉上都是"卡住"，分不清 |
| `验收：…` | 完成标准 | ✅ |
| `… 另有 N 条已完成/已延后` | 折叠计数 | ⚠️ 没给"怎么看它们"的命令 |
| **每条该敲什么** | 全区一条命令都没有；只有页脚给一条 `解锁 zloop edit t1 --status open`，多条被阻塞时其余要自己推 | ❌ **主诉求 2 没被满足** |

## 三、明细行（灰标签）

| 元素 | 现状 | 判定 |
|---|---|---|
| `阶段` | 只在"有新消息"时才出现 | ❌ 就绪 / 已暂停 / 完成 三种状态**根本没有这一行** |
| `阶段` 的内容 | `t1 · 第 1 轮 · 已跑 0s · claude`、`13:27 醒来 · 还有 4m11s`、`本窗口次数用完 · 1440 分钟后重试` | ⚠️ 前两条清楚；`1440 分钟` 该写成 `约 24 小时` |
| `后台` | 只在 runner 有 pid 时出现 | ⚠️ 没跑时完全不提，用户分不清"没人跑"和"忘了看" |
| `睡眠` | `合盖不休眠 · 1 个 runner 在跑` | ✅ |
| `文档` | `1 轮缺实现思路 · zloop log 里带 ⚠` | ✅ |
| `会话` | `claude --resume <id>` | ✅ 可直接抄 |

## 四、命令行（青标签）

| 状态 | 现在给的命令 | 判定 |
|---|---|---|
| 就绪 | `开跑 zloop start` | ✅ |
| 执行中 | **没有** | ❌ 用户不知道该等它还是该插手 |
| 休眠中 | `开跑 zloop start` | ⚠️ 前台 `zloop run` 在跑时没有 pid 文件，会劝你再开一个 |
| 等你决定 | `解锁 zloop edit t1 --status open` | ⚠️ 只覆盖第一条 |
| 限流中 | **没有** | ❌ 不知道能不能调、去哪调 |
| 已停 | `看失败 zloop log` / `重跑 zloop start` | ✅ |
| 已暂停 | `继续 zloop resume` | ✅ |
| 完成 | `加活 / 换目标 / 出文档` | ✅ |

## 五、结论：3 个 ❌ + 9 个 ⚠️

必改（对应用户的两个诉求）：

1. **阶段永远有一行**，并且明说它是阶段——不管什么状态都能答出"现在在哪一步"。
2. **待办每条自带状态词和命令**——`下一个 / 等你回话 / 排队中 / 等 t2`，被阻塞的那条把解锁命令直接放在它自己下面。
3. **执行中、限流中补上动作行**。

顺手改：计数和花费用人话（`完成 0/4 · 执行 3 轮 · 花了 $2.31 / 上限 $5.00`）、`1440 分钟` → `约 24 小时`、后台没跑时也说一句、折叠行给命令。

→ 落实在 t9 / t10 / t11。

## 六、改完之后（2026-08-28，t9–t11）

| 原判定 | 改成什么 |
|---|---|
| ❌ 阶段不常驻 | `阶段` 行任何状态都在；phase 没有新消息时由状态兜底成一句人话（"4 条待办全部完成，目标结束" / "你按了暂停，待办原地保留" / "没人在跑 · 下一条是 t1"） |
| ❌ 待办无指令 | 每条待办自带状态词（执行中 / 下一个 / 等你回话 / 等 t3 / 排队中）；被 `--block` 的那条把 `答完敲 zloop edit <它自己的 id> --status open` 贴在自己下面 |
| ❌ 执行中、限流中无动作 | 执行中 → `写回 zloop done <id> --note … --approach …`；限流中 → `放宽 改 policy.max_runs` |
| ⚠️ `0/4 todo · 3 轮 · $0.25/2.00` | `0/4 条待办 · 跑了 3 轮 · 花了 $0.25（上限 $2.00）` |
| ⚠️ `1440 分钟后重试` | `约 1 天后重试`（`human_minutes`：90 分钟以上说小时，一天以上说天） |
| ⚠️ 后台没跑时不提 | `后台` 行常驻，明说"没有 runner 在跑" |
| ⚠️ 休眠中却劝你 `zloop start` | 休眠 = 有 runner 在跑（只是前台 `zloop run` 不写 pid），改成给 `看日志` |
| ⚠️ 折叠行没命令 | `… 另有 3 条已完成/已延后 · zloop log 看它们的记录` |
| ⚠️ `⏳` 不说等谁 | 直接写 `等 t3` |
| ⚠️ `解锁` 只覆盖第一条 | 下沉到每条自己下面，页脚那条删掉 |
| ⚠️ 执行中的 todo 显示"下一个" | `state.in_progress` 命中的那条显示 `🔄 执行中` |

8 种状态的实拍已贴进 README（两屏正文 + 其余 6 屏折叠），三个问题逐屏复核过：**在哪一步 / 还剩什么 / 我该敲什么**，8/8 都能只看这一屏答出来。

## 七、第二轮反馈：清单要带勾（2026-08-28，t12）

用户看完上面的改动后仍指出一处缺口——**完成态把清单整个藏了**，看不到"做过哪几步"：

> 应该再列出：目标：xxxxxx / 阶段:2/3 / 1、xxx ✅ 2、xxx ✅ 3、xxx running

审查表第二节把待办区判成 ⚠️（"符号猜不出语义"），漏判了一件更基本的事：**它只列没做完的**。
做完的那些一旦从屏幕上消失，"进行到第几步"就只剩一个百分比，复盘时最想看的"做过什么"完全没有。

| 原来 | 改成 |
|---|---|
| 只列没做完的；完成态一条不列 | `步骤` 清单列**全部**步骤，编号 + 文本 + 右栏状态，做完的打 `✅` 留在原位 |
| 目标文字是标题下面一行裸文本 | `目标` 变成带标签的一行，和 `阶段` / `后台` 对齐 |
| 标题里 `11/11 条待办` | 计数移到 `步骤 11/11 完成`（标题只留百分比、轮数、花费，不重复） |
| `⏳ 等 t3` | `⏳ 等第 3 步`（用步骤号，和清单编号对得上） |
| 依赖只看 `status == "blocked"` | 按 `todo::is_executable` 的口径看 `blocked_by`：依赖没 done 就算被挡，`status` 仍是 `open` 也算 |
| 长清单 | 超过 15 步折叠：没做完的全留，前面垫 3 步做过的，其余收成 `…  前 11 步已收起` |
